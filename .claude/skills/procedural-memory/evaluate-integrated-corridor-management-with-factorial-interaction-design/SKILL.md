# Evaluate Integrated Corridor Management with Factorial Interaction Design

Determines whether individually-proven ITS measures (diversion, ramp metering, responsive signals, VSL) compose when deployed together during an incident — the question that decides whether a real ICM deployment is worth funding, and one nothing in memory had measured before this skill, since every prior ITS skill studies its own measure in isolation on a network built to isolate it.

## Build a corridor with a genuine, non-dominated tradeoff

The freeway-vs-arterial diversion choice is only a real design question if the arterial is a real alternative — neither so fast it dominates the freeway nor so slow no one would take it. **Verify the tradeoff numerically before building anything else**: measure free-flow travel time on both paths over a matched span and target roughly 15–30% arterial slower than freeway. This is a real calibration exercise, not a given — an initial network with too large a freeway/arterial speed differential produced a tradeoff far outside any realistic band before any signal delay was even added; iterating the design speeds and signal cycle/spacing together (not just one parameter) was needed to land in range with genuine, non-zero, non-resonance-engineered signal delay.

**Direction-specific merge type matters more than it looks.** A single "fix" (switching all interchange merges to a cooperative zipper merge to eliminate one direction's yield-related teleports) can silently introduce a *new* teleport-jam cluster in the opposite direction, even with zero incident and reduced demand. Diagnose by teleport-lane frequency, not by direction-agnostic aggregate counts, and don't assume a merge-type fix that helps one direction is safe to apply uniformly — it may need to be direction-specific.

## Audit every control module — confirm it actually acts, don't assume configuration equals behavior

**Report realized behavior, not configured parameters, for every module.** A diversion-advisory compliance share configured at 50% should be checked against the realized diversion share measured from actual vehicle routing decisions (not just the compliance parameter echoed back); a ramp meter's configured target rate should be checked against its realized discharge rate and queue length; a VSL's configured compliance should be checked against measured speed-adherence in the control zone; a responsive signal plan's activation should be checked against an actual logged program-switch event at the expected trigger time, not assumed from the controller code path executing without error. This audit step catches real bugs — e.g. a signal offset formula that assumed every junction's coordinated phase started at local phase-time zero (false for some junctions) silently degraded the arterial's actual coordination while the code ran without any error, and was only caught by inspecting each junction's own compiled connection map.

**A response-triggered control module needs an explicit stand-down condition, or its measured effect will be confounded with how long it stays armed.** A module that activates on incident detection but never re-checks whether the incident has since cleared will remain active for the rest of the demand window by construction. This is not automatically wrong, but it materially shapes downstream findings — a response-lag sweep's "harm shrinks with longer lag" result can be an artifact of a shorter active window (less demand exposed to the module before the simulation ends) rather than a genuine finding about response speed, and a duration/severity sweep's "shorter incidents are harmed more" result can likewise be an artifact of the same fixed-window mechanism rather than a property of the incident itself. If a control module lacks a stand-down condition, disclose this explicitly wherever it could explain a directional pattern in the results — don't let it silently masquerade as a substantive finding.

## Connect detection to response, and treat total response lag as a design variable

Reuse an existing AID (automatic incident detection) algorithm to drive control-module activation rather than assuming an oracle-instant response — measure the detector-latency distribution over CRN seeds, then sweep total response lag (detection + decision + activation, including a 0-lag oracle arm as an upper bound on achievable benefit) as an explicit curve. This produces the deployment-relevant answer ("how much benefit does a realistic 5–10 minute response lag destroy") that a single-lag study cannot.

## Transfer the CRN-paired factorial/interaction methodology from parameters to policies

`screen-and-decompose-sumo-parameter-sensitivity` and `discrete-network-design-and-project-interaction` establish the noise-floor-gated, CRN-paired-bootstrap discipline for measuring whether combined effects are additive — this skill's core methodological contribution is transferring that machinery from *parameters* (or discrete infrastructure projects) to *control-measure combinations*. Run the complete 2^k factorial (all combinations of k binary control measures) under Common Random Numbers, with enough seeds to establish a noise floor (2×SEM is a reasonable default gate), then estimate every main effect and two-way interaction with a **CRN-paired bootstrap** — resample whole per-seed differences, never two independent samples from each arm's raw values. This distinction is not cosmetic: an unpaired bootstrap on the same data can produce a visibly wider, wrong confidence interval that doesn't reproduce under the paired method, precisely because it discards the variance reduction the CRN design was built to provide. Verify which method any bootstrap-CI code in your pipeline is actually using — a one-off "unpaired" implementation can silently creep into an otherwise-correct paired pipeline (e.g. copied from a different, non-CRN context) and produce numbers that look plausible but don't reproduce under the codebase's own established method elsewhere.

**Gate every effect against the noise floor before calling it a finding**, distinguishing "statistically significant" (CI excludes zero) from "resolvable" (magnitude exceeds the replication noise floor) — a main effect or interaction can be nominally significant yet still smaller than what CRN replication noise alone can produce, in which case it should not be reported as a real, actionable effect.

**One dominant measure can make the rest of the factorial statistically uninformative about interactions, and this is itself a finding worth reporting plainly.** If one control measure's main effect vastly exceeds every other measure's main effect and every two-way interaction (by an order of magnitude or more), the factorial's power to detect genuine interactions involving the smaller-effect measures collapses — a null interaction result in that regime should be reported as "cannot be resolved from noise given this replication count," not as "no interaction exists." Don't force a confident interaction claim the data can't support just because the factorial design nominally estimates it.

## Distributional accounting: who pays for a corridor-level number

Decompose the outcome by user group (e.g. never-diverted through traffic, diverted traffic, parallel-facility through traffic, local/cross-street traffic) using route- or trip-tagged demand generation from the start, not post-hoc guessing. A corridor-level aggregate can hide that the group paying the largest *individual* per-person cost (e.g. diverted drivers) is not the group bearing the largest *aggregate* system cost (e.g. a much larger non-diverted population absorbing a smaller per-person but system-wide slowdown) — report both the per-person and the aggregate view, since they can point to different "who pays" answers. Pair this with a scope-limited safety proxy (e.g. queue-front hard-braking events) and disclose explicitly what it does and doesn't instrument (a freeway-queue-front proxy says nothing about conflict risk on a diversion path it doesn't cover).

## Gotchas

- **SUMO activates the *last-loaded* `tlLogic` program as a junction's default** — if you write a "baseline" plan before an "incident-response" plan for the same signal id, every run will silently start in the incident-response plan regardless of whether an incident has occurred. Verify the active program via `traci.trafficlight.getProgram()` at t=0, don't assume file-write order is harmless.
- **A collection/aggregation script run against a still-running background batch will silently produce an incomplete dataset with no error** — file mtimes are the tell (collected-output timestamp earlier than the last raw-output timestamp). Always confirm a batch's manifest/completion status before trusting its aggregated output, especially after resuming from an interruption; re-running collection against already-complete data costs nothing and is the correct fix, not a re-run of the underlying simulation.
- **`getIDList()` or equivalent per-step TraCI enumeration calls inside a per-vehicle loop is an O(n²)-per-step performance trap** — call once per step and index into the result, not once per vehicle per step; this can make one control module an order of magnitude slower than structurally similar ones with no functional difference.
